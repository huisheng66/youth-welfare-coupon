# 存量服务器更新指南

面向**已部署运行**的服务器（区别于 `install-ubuntu.sh` 的首次安装）。
更新一次发布涉及三个环节：构建 → 同步 dist → Nginx 配置。**顺序不能颠倒。**

---

## 更新前必读：两个会导致服务起不来的坑

### 坑1：`brotli` 指令会让 Nginx 启动失败

构建产物 `dist/_assets-cache.conf` 内含：

```nginx
brotli_static on;
brotli on;
```

这两个指令**要求 Nginx 编译时带 `--with-http_brotli_module`**。
若目标机器没有该模块，`nginx -t` 直接报 `unknown directive "brotli_static"`，
**该 server 块无法加载 → 整站 502/404**。

上线前先确认目标机器是否支持：

```bash
nginx -V 2>&1 | tr ' ' '\n' | grep -E 'brotli|gzip_static'
```

- 有 `brotli` → 可直接用生成的片段
- **只有 `gzip_static` → 必须删掉 `brotli_static on;` 和 `brotli on;` 两行**

`install-ubuntu.sh` 内置了模块探测（无 brotli 时生成空片段），所以一键安装不会踩坑；
但**存量服务器直接替换片段时极易踩中**。

### 坑2：`add_header` 在同一层是覆盖而非叠加

Nginx 的 `add_header` 规则：

- **不同 location 之间**：完全不继承（易被忽视）
- **同一 location 内多条**：后写的覆盖先写的

所以在已有安全响应头的 location 里再加 `add_header Cache-Control ...`，
会把 CSP/HSTS/X-Frame-Options **全部冲掉**。正确做法是写进同一层，并确认响应头实际存在：

```bash
curl -sI https://<域名>/assets/index-*.js | grep -iE 'content-security-policy|strict-transport|x-frame'
```

另外 `expires` 指令会**额外产出**一条 `cache-control`，与 `add_header` 产生的重复。
只用 `Cache-Control` 控制缓存时长，不要同时写 `expires`。

## 标准更新流程

```bash
# 0. 本地构建（BUILD_ID 可显式指定，便于追溯）
cd frontend && npm ci && npm run build
# 注入默认构建号（时间戳）；CI 里建议：BUILD_ID=$(git rev-parse --short HEAD) npm run build

# 1. 备份（必做，nginx 配置与 dist 都要）
ssh <host> 'cp -a /etc/nginx/sites-available/<site> /etc/nginx/sites-available/<site>.bak-$(date +%s)'
ssh <host> 'cp -a /opt/welfare/frontend/dist /opt/welfare/frontend/dist.bak-$(date +%s)'

# 2. 打包并上传
tar -czf /tmp/dist.tgz -C frontend/dist .
scp /tmp/dist.tgz <host>:/tmp/dist.tgz

# 3. 解压到新目录，再原子替换（避免中途 404）
ssh <host> 'rm -rf /opt/welfare/frontend/dist.new && mkdir -p /opt/welfare/frontend/dist.new \
  && tar -xzf /tmp/dist.tgz -C /opt/welfare/frontend/dist.new \
  && chown -R www-data:www-data /opt/welfare/frontend/dist.new \
  && cd /opt/welfare/frontend && mv dist dist.old.$(date +%s) && mv dist.new dist'

# 4. 按「坑1」处理 _assets-cache.conf，再更新 Nginx 配置
# 5. 校验并重载（顺序不可颠倒）
ssh <host> 'nginx -t && systemctl reload nginx'
```

> **第 5 步不可跳过**：`nginx -t` 失败时不要 reload，否则旧配置被覆盖、
> 新配置又起不来，站点直接不可用。备份就是为了此时能回滚。

## 更新后验证清单

```bash
# 可访问性
curl -so /dev/null -w '%{http_code}\n' https://<域名>/            # 期望 200

# 缓存策略（/index.html 不缓存、/assets/ 长缓存）
curl -sI https://<域名>/index.html | grep -i cache-control        # 期望 no-cache
curl -sI https://<域名>/assets/index-*.js | grep -i cache-control # 期望 max-age=31536000

# 安全头没被 add_header 覆盖掉（对应「坑2」）
curl -sI https://<域名>/assets/index-*.js | grep -icE 'content-security-policy|strict-transport'

# 预压缩是否生效（需客户端支持）
curl -sI -H 'Accept-Encoding: gzip' https://<域名>/assets/index-*.js | grep -i content-encoding
```

浏览器侧再确认一遍：强制刷新（Ctrl+Shift+R）后页面正常、
DevTools Network 里入口 JS 已换成新hash。

## 发版后用户仍报 Axios 400？

大概率不是服务端故障，先核对堆栈里的 JS 文件名：

```bash
ls /opt/welfare/frontend/dist/assets/ | grep -i <报错里的hash>
```

- **服务器上不存在该文件** → 浏览器加载的是发版前的旧版本，属于旧页面问题
- 刷新（Ctrl+Shift+R）即可；本项目已内置构建号检测自动刷新机制
- 若**存在**该文件，再去查接口本身的校验逻辑

另外，登录接口返回 **400 是业务正常响应**（`邮箱/用户名或密码错误`），
不是服务端异常，排查时别误判：

| 情况 | 状态码 | 含义 |
|---|---|---|
| 缺 `X-Requested-With` | 403 | 缺 CSRF 校验头 |
| 缺 `username`/`password` | 422 | FastAPI 参数校验 |
| 凭据错误 | 400 | 账号或密码错误 |

## 回滚

```bash
cp -a /etc/nginx/sites-available/<site>.bak-<时间戳> /etc/nginx/sites-available/<site>
cp -a /opt/welfare/frontend/dist.bak-<时间戳> /opt/welfare/frontend/dist
nginx -t && systemctl reload nginx
```
