## 1. 问题清单

优先级采用代码审查约定：P1 为应优先修复的正确性/安全问题，P2 为应修复的功能缺失。以下均有本次独立验证结果，不能用现有 135 项测试通过替代。

### F01 [P1] 临界过期处理能覆盖已经成功核销的状态

位置：`backend/app/api/coupons.py:589`，特别是紧接 `_maybe_expire(coupon)` 的 `db.commit()`。

`_maybe_expire` 根据 session 中已读取的对象判断状态，再以普通 ORM 更新保存 `expired`。此更新只有主键条件，没有 `status == unused` 条件。新增加的作废前提交会在后面的作废条件 UPDATE 执行之前，先把另一个请求已经写入的 `used` 覆盖掉。

本次复现步骤：

1. 会话 A 读取一张 `unused` 券，保留对象。
2. 会话 B 在有效期内通过真实 `/api/coupons/redeem` 成功核销，HTTP 200，并提交成功流水。
3. 将 A 的业务时钟推进到券有效期之后，调用实际 `void_coupon`。
4. A 因判断已过期返回 HTTP 400，但此前的 commit 已覆盖 B 的状态。

实测结果：`redeem_http=200`、`void_http=400`、`final_coupon_status=expired`、`success_log_count=1`。券终态与核销证据互相矛盾。

修复要求：过期转换同样使用 `WHERE status = unused AND expires_at <= now` 的条件更新，不能从旧 ORM 对象盲写终态。统一检查预览、出码、核销、作废中的 `_maybe_expire` 调用，避免只修一个入口。作废自身也应在最终状态更新时核验有效期。

补测：固定“先读旧状态、另一会话核销、跨过期点、旧会话继续”的交错次序，断言终态保持 `used`，成功流水唯一，失败尝试原因正确。当前仅在请求开始处使用 Barrier 的竞争测试没有覆盖此窗口。

### F02 [P1] 验证码并发消费未原子检查错误次数和有效期

位置：`backend/app/services/mail.py:257`、`:269`。

错误次数和过期时间在读取后于 Python 中检查；错误次数 UPDATE 仅限定 ID，正确码消费 UPDATE 仅限定 ID 和 `used_at IS NULL`。在读取与更新之间，其他请求可能已把错误次数增至上限，当前请求仍会成功消费。批量并发请求也能同时越过旧计数检查，使一次验证码被实际校验的次数超过设置上限。

本次通过受控交错复现：A 读到 `attempts=4`；在匹配验证码前，B 将该行更新为 `attempts=5` 并提交；A 继续提交正确码。结果为 `locked_code_attempts=5` 且 `consumed_after_lock=true`。

修复要求：为错误计数和正确消费建立共同的原子资格边界，至少覆盖未消费、未过期和次数未达上限。可采用受控事务内行锁，或把资格条件加入条件更新并根据影响行数处理冲突。不能仅给成功分支补条件，而让错误分支继续无上限增量处理。

补测：错误请求与正确请求竞争、多个错误请求同时跨越上限、等待期间过期，以及两个正确请求并发消费。`test_concurrent_consume_single_winner` 当前依次调用 `attempt(s1)`、`attempt(s2)`，本质是串行复用测试，需增加真实交错验证。

### F03 [P1] MySQL 首次时长开户竞争失败后仍读取旧快照

位置：`backend/app/services/points.py:34`，特别是异常分支的普通 `.first()`。

在 MySQL 默认 `REPEATABLE READ` 下，首次查询“账户不存在”会建立一致性读取快照。另一事务随后创建账户并提交时，本事务的 INSERT 可以通过唯一约束检测发现冲突，但回滚 savepoint 不会重置整个事务的读取快照。异常分支再次执行普通 SELECT 仍得到不存在，随后重新抛出 `IntegrityError`。

本次使用**一次性独立 MySQL 8.4 实例**验证，未连接现有业务库：

1. A 普通查询确认时长账户不存在。
2. B 调用实际 `get_or_create_account` 创建并提交。
3. A 调用同一函数，插入发生唯一冲突，进入重查分支。

实测：隔离级别 `REPEATABLE-READ`，返回 `IntegrityError after competing insert committed`。该错误在业务入口未被转换为正常冲突恢复，会导致请求失败。SQLite 的并发开户测试通过不能证明此处兼容 MySQL。

修复要求：冲突后使用能看到已提交胜者的当前读，例如适当的锁定读取；或使用经验证的数据库 upsert 方案。不能简单 rollback 整个外层事务，避免丢掉调用方尚未提交的业务写入。

补测：MySQL 两个独立连接固定交错，断言仅一个账户、两笔成功时长调整各有账本、余额正确，且无 500；账户创建失败后不破坏外层事务。

### F04 [P2] 密钥扫描漏掉本项目的数据库 URL 和 SSH 密码格式

位置：`scripts/scan_staged_secrets.py:48`、`:49`。

密码变量规则识别 `password/passwd/pwd`，不识别部署脚本使用的 `SSH_PASS`；数据库 URL 规则识别 `mysql://`，不识别项目实际使用的 `mysql+pymysql://`。因此把真实密码按现有部署变量形式硬编码到新增脚本时，该新增 CI 门禁可能仍通过。

本次仅用合成凭据直接调用实际 `scan()`：

| 合成输入形式 | 扫描结果 |
| --- | --- |
| `DATABASE_URL="mysql+pymysql://review:<合成密码>@localhost:3306/welfare"` | `[]`，漏检 |
| `SSH_PASS="<合成密码>"` | `[]`，漏检 |

修复要求：覆盖现有技术栈的带驱动 scheme，以及 `SSH_PASS/DB_PASS` 等项目实际命名；区分字面量与环境变量引用，并继续脱敏输出。优先考虑成熟扫描规则，不通过排除整个部署目录消除误报。

补测：暂存差异中两种合成凭据都被阻断，环境变量注入通过；测试应验证扫描脚本退出码，而不只测试正则函数。

### F05 [P2] 门店停用后的核销拒绝没有失败流水

位置：`backend/app/api/coupons.py:678`。

代码在门店停用时直接抛出 400，没有调用失败核销记录函数。虽定义了 `merchant_inactive` 原因常量，但该分支没有使用。已鉴权商家的一次业务核销尝试因此无法在流水中查询，也不满足 T06 对业务失败留痕的要求。

本次复现：用户取得有效动态码；门店停用；已登录商家提交核销。实际 `inactive_redeem_http=400`，该门店失败流水数量为 `0`。

修复要求：门店记录存在但停用时，持久化一条 `merchant_inactive` 失败记录后再返回拒绝，确保不改变券状态。门店缺失或账号无绑定等无法满足外键的情况应单独定义日志路径，不能直接插入无效外键。

补测：验证拒绝状态、失败原因、所属商家/操作者以及券保持原状态。
